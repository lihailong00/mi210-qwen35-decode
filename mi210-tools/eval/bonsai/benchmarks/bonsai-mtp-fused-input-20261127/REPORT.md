在同一版 llama-server 上，K=3 的单请求生成吞吐从 142.57 提至 152.64 token/s（+7.1%）。每轮最多起草 3 个 token，接受 848/1272（66.67%）。关闭和开启融合各独立启动三次，每次运行同五条提示，各生成 256 个 token。

K=3 各轮关闭为 143.46, 142.49, 141.75，开启为 152.39, 154.24, 151.32 token/s。表中按总生成 token 除以总生成时间聚合。连同提示处理及本机 HTTP 往返，五条短提示的总吞吐从 126.36 提至 134.45 token/s。单请求、贪心、seed 1、提示缓存关闭、8192 上下文、batch 和 ubatch 均为 4096、FA 开启、F16 KV。K=0 的单列生成沿用既有内核。

## 每轮时间

五条提示共 425 个验证轮，平均交付 3.012 个 token。按常规服务吞吐折算，关闭为 21.13 ms/轮，开启为 19.73 ms/轮，节省 1.39 ms。相同接受情况达到 200 token/s 需要 15.06 ms/轮，仍需节省 4.67 ms。

下表来自独立插桩的服务运行，每种状态各 3 个进程，共 1,275 轮。两栏取全部轮次的算术平均。

|---|---:|---:|
| 主模型验证 | 17.55 | 16.82 |
| 草稿生成 | 3.06 | 2.77 |
| 草稿状态追赶 | 0.19 | 0.19 |

| 总计 | 21.31 | 20.29 |

## GPU 追踪与下一个优化目标

每种状态另取最后 20 个完整四列主模型验证轮。将同一输入的符号乘法、1024 点 Hadamard 变换和 Q8 量化合成一次 GPU 启动，再让共享输入的 1–3 个投影复用结果。每个完整轮次包含 129 个单投影组、112 个双投影组和 16 个三投影组。

| 每个完整验证轮 | 关闭融合 | 开启融合 |
|---|---:|---:|
| 主模型全部 GPU 内核启动 | 1,821 | 1,019 |
| 输入准备启动 | 257 符号乘法 + 257 变换 + 401 量化 | 257 次融合准备 |
| Q2_0 投影启动 | 401 | 257 |
| Q2_0 矩阵合计（ms） | 11.75 | 10.91 |
| 其中 FFN gate/up（ms） | 4.76 | 4.49 |
| 其中 FFN down（ms） | 2.43 | 2.41 |
| 输入准备及投影合计（ms） | 15.87 | 12.70 |

优先测试 FFN 的 Q2_0 × Q8 四列 MFMA 内核。gate/up 和 down 合计 6.89 ms，占矩阵耗时的 63.2%。单独用 FETCH_SIZE 对 15 轮采样，每轮两者分别读取 3.21 和 1.61 GB，计数器运行下各约 643 和 603 GB/s。此前用相同投影顺序和权重布局做纯读重放，7.20 GB 用 6.27 ms，约 1,148 GB/s。完整计算还要解包、矩阵乘累加和归约。

先在 5120→17408 的成对 gate/up 上，比较现有循环与提前读取下一组权重编码和缩放因子的版本。保留当前浮点归约顺序，测量增加的寄存器占用是否抵消收益。再对 17408→5120 的 down 单独筛选。若相同服务轮次能回收 1 ms，短提示吞吐可到约 161 token/s。此数为条件估算。

## 正确性、显存与重现

- 所有短请求的文本和 token ID 均与各自无 MTP 贪心参考一致。K=3 的整卡显存采样峰值为 18.40 → 18.40 GiB。
- 4,096-token 输入追加 256 个 token 的独立抽查为 151.26 → 154.45 token/s，两次都接受 183/214 个草稿，输出与相同长提示的参考逐 token 一致。每种状态只运行了一次。
- 34 个原有 Q2_0 算子案例通过。另在 35 张图上各执行三组输入，覆盖三种实际宽度、1–3 个投影、2–4 列、同图更换输入和符号、全零、显式中间输出、额外消费者和回退形状。开关两态的 435,864 个 FP32 输出逐字节相同。独立测试 trace 实际捕获 81 次融合准备、54 次分组矩阵核。
- 512-token Bonsai 和 128-token Qwen IQ3_S 的完整原始 logits 分别与已保存的参考文件逐字节一致。哈希、每次请求的耗时、显存和计数器数据见 results.json。
- 验证平台为 MI210 gfx90a、ROCm 7.2.1。开关默认为开，设置 GGML_MMVQ_Q2_0_FUSED_INPUT=0 并重启测试进程可运行基线。两态均使用上一版四行交错布局。

~~~bash
cmake --build build --target ggml-hip llama-server test-backend-ops -j 6
./build/bin/llama-server -m "$MODEL" -dev ROCm0 -ngl 99 -fa on -t 8 -b 4096 -ub 4096 -ctk f16 -ctv f16 -c 8192 -np 1 --spec-type draft-mtp --spec-draft-n-max 3
~~~

在前一版四行交错优化的源码基础上应用增量补丁 q2-fused-input.patch。补丁内的 mi210-tools/eval/bonsai/fwht-group-check.cpp 可在两次独立进程中写出原始结果，再用 cmp 比较。
