# Bonsai 27B 的 MI210 四行交错权重优化

单卡 MI210，K=3、单请求，综合 decode 从 118.86 提至 142.21 token/s（+19.6%）。新布局让四条相邻 GPU 线程从连续地址读取四行权重，单 token 和多 token 内核共用同一份无损重排缓存。

| 每次最大草稿数 | 原布局 token/s | 四行交错 token/s | 变化 | 每种布局独立启动次数 |
|---|---:|---:|---:|---:|
| 关闭 MTP | 78.70 | 83.78 | +6.5% | 3 |
| 1 | 99.60 | 103.81 | +4.2% | 2 |
| 2 | 107.43 | 131.70 | +22.6% | 3 |
| 3 | 118.86 | 142.21 | +19.6% | 3 |

同一版 llama-server，开关交替运行。每次依次测试英文续写、Python、中文解释、算术、JSON 五条提示，每条生成 256 token。指标按总输出 token 除以服务报告的总 decode 秒数计算。每个请求的输出文本和 token 都与无 MTP 的参考一致。贪心、固定种子、关闭提示缓存、单槽位、8192 context、batch/ubatch 4096、FA 开启、F16 KV。

K=3 新布局三次速度为 142.65, 142.73, 141.25 token/s。两种布局每次都接受 848/1272 个草稿 token。K=3 进程运行期间，采样到的整卡显存峰值分别是 18.40 和 18.40 GiB。早期两份缓存的实验会多占约 7 GiB，最终使用单份缓存。

单条 4,096-token 输入续写 256 token，原布局 127.32、新布局 148.09 token/s。两次输出与该条无 MTP 参考完全一致，仅作长输入抽查。

另测 llama-bench 的单 token 解码 tg128，原布局 79.60、新布局 83.63 token/s。pp8192（ubatch=4096）从 1956.4 到 1954.5 token/s。

筛选阶段对同一矩阵图分别测量原布局、仅改四行交错、再对完整 32 槽分组消除尾部判断。四列 gate/up 为 66.4 → 58.7 → 55.7 µs，down 为 71.9 → 67.7 → 56.1 µs。独立矩阵图时间包含启动、激活量化和输出，正式吞吐取自上表的服务器测量。

## 使用与正确性

当前构建在 gfx90a 上默认启用。可用服务器参数 `--spec-type draft-mtp --spec-draft-n-max 3` 启动 K=3。环境变量 `GGML_MMVQ_Q2_0_TILE=0` 切回上一版布局。原 Q2_0、MFMA 和多列验证开关继续生效。

沿用 Q2_0 原有权重筛选条件，并要求输入维度为 1024 的整数倍。每 32 个值的编码四行交错，对应的 FP16 缩放因子也按四行交错。对齐形状无需处理不完整的 32 槽分组，2/3/4 列共用 MFMA 路径。单列保留寄存器累加次序及 SwiGLU、残差融合。原 GGUF 文件保持原样。

34/34 项 ROCm 算子测试通过。连续、带偏移及行间距的输入共 36 组，覆盖 6 个输入宽度和 2/3/4 列，含零块与舍入边界。两种布局各自与单列调用逐位一致，同时跨布局比较的 27,648 个 F32 输出也逐位一致。

Bonsai 的 512-token 原始 logits SHA-256 与已有基准一致（`c078223d85c0b6ab81ed46add482bd2a64171fe2b2a535151615194f7159c4b8`）。Qwen IQ3_S 的 128-token logits 也与已有基准一致（`a16e39a8386a261a3ee094c0ae26d0009c9f5aadf84e33233d5803dd53ac16ae`）。
