# MI210 上 Bonsai Q2_0 八列验证实测

Ternary-Bonsai-2.5-27B 在单卡 MI210 上生成时，每个完整八列验证轮的 Q2_0 矩阵投影由 **20.41 ms 降至 14.01 ms**，达到 14–15 ms 的目标。九条常规请求合计，原生 MTP7 从 103.3 升至 128.2 token/s，Bonsai 2 微调 DFlash7 从 102.1 升至 130.0 token/s。同场原生 MTP3 为 145.5 token/s。

## 真实权重与真实激活

| 测量范围 | 原八列，ms/轮 | 新八列，ms/轮 | 节省，ms/轮 |
|---|---:|---:|---:|
| 真实权重重放，两次独立进程 | 20.33 / 20.33 | 13.83 / 13.84 | 6.50 / 6.49 |
| 原生 MTP7 生成时，257 次 Q2_0 投影之和 | 20.41 | 14.01 | 6.39 |
| 同轮输入变换与 Q8 准备 | 3.13 | 2.11 | 1.02 |
| 每轮内合计投影与输入准备，再取中位数 | 23.54 | 16.12 | 7.42 |

重放从原 GGUF 读取 64 层加词表输出的全部 401 个目标模型 Q2_0 矩阵，按实际推理顺序组成 257 组。每组使用独立生成的八列 Q8 输入，共用输入的投影仍共享同一份激活。每个进程取 12 次交错测量的中位数，每次计时三遍 HIP Graph，排除读盘与权重重排。两种随机种子各比较 33,181,696 个 FP32 输出，新八列、旧八列和两次独立四列投影逐位一致。交付的独立 HIP 源码另行编译运行，原八列和新八列分别为 20.33 和 13.94 ms，逐位差异为零。

真实激活取自 llama-server 的一条英文续写，每组生成 112 个 token。rocprofv3 分别捕获了 40 个完整八列验证轮，各取最后 20 轮。表中计时是主模型验证范围内对应 GPU 内核执行时间的和。优化前后每轮各运行 257 次投影，输入准备从 514 次降到 257 次。服务端吞吐另用关闭 profiler 的进程测量。

## 常规请求的生成速度

每种配置在三个独立服务进程中各跑一遍九条提示。每条固定生成 256 个 token，单槽、贪心、seed 1、关闭提示缓存，排除热身。标准五题是英文续写、Python 有序列表合并、中文解释、算术和 JSON。留出四题是中文小词典、英文改写、Python 滚动中位数和中文 JSON。每轮轮换提示顺序，同一 A/B 配对使用相同顺序，第二轮对调新旧内核的运行顺序。

| 配置 | 标准五题 token/s | 留出四题 token/s | 九题合计 token/s | 九题含 prefill 的 HTTP token/s |
|---|---:|---:|---:|---:|
| MTP7 原八列 | 109.1 | 96.9 | 103.3 | 95.1 |
| MTP7 新八列 | 133.6 | 122.1 | 128.2 | 115.7 |
| DFlash7 原八列 | 106.1 | 97.5 | 102.1 | 94.5 |
| DFlash7 新八列 | 135.9 | 123.2 | 130.0 | 117.3 |
| MTP3 四列对照 | **149.9** | **140.4** | **145.5** | **129.8** |

前三个速度列沿用项目口径，用总输出 token 数除以服务端总生成时间。最后一列用总输出 token 数除以客户端请求 `/completion` 的总墙钟时间。服务端另有扣除每条首 token 的速度字段，其对应的分组合计也在 results.json 中。GPU 全卸载、FA 开、F16 KV，上下文容量 8192，batch 和 ubatch 均为 4096。DFlash 使用项目此前核验过的 Bonsai 2 微调 Q4_K_M 草稿和目标权重 Hadamard 变换修正。所有配置均在实际请求中计算草稿及验证结果。

| 配置 | 优化前后九题生成时间，ms/验证轮 | 九题输出 token/验证轮 |
|---|---:|---:|
| MTP7 | 35.92 → 28.95 | 3.71 |
| DFlash7 | 34.26 → 26.90 | 3.50 |
| MTP3 | 20.12 | 2.93 |

新八列将九题合计 decode 吞吐分别提高 24.1% 和 27.3%。DFlash7 的 Python 有序列表合并、算术和 JSON 分别达到 209.1、218.4 和 214.7 token/s，英文续写为 84.4 token/s。以九题的 DFlash7 轮时 26.90 ms 推算，达到 200 token/s 需要平均每轮产出 5.38 个 token，实测为 3.50。上述轮时由 HTTP 生成阶段时间除以实际验证轮数，包含提议、验证及生成循环开销。

135 个计时请求的 token ID 和文本均逐条等于同提示无推测贪心参考。54 对新旧八列请求的草稿数、接受数、验证轮数、输出 token ID 和文本也全部一致。另用 3 个输入宽度、5–8 列和 1–3 个投影的组合检查了服务后端，247,104 个 FP32 结果逐位等于此前的参考结果。

## 实现与复现

每个线程块处理 8 个输出行和 4 个输入列，相邻线程块分别计算八列的前后半段。GPU 缓存中将两个四行组的二位码和 FP16 scale 成对排布，使用向量加载。输入宽 5120 采用 64 线程并交错计算两组点积，宽 6144 和 17408 采用 128 线程。三种宽度保留原浮点归约次序。八列的符号变换、Hadamard 变换和 Q8 输入准备一次启动完成。GGUF 中的 Q2_0 权重原样读取。

专用 GPU 权重副本的有效载荷为 7,199,539,200 字节，约 6.71 GiB。实验期间按同一方法采样的整卡稳定显存，MTP7 约从 18.97 升至 25.99 GiB，DFlash7 约从 24.79 升至 31.81 GiB。

八列补丁针对项目包含既有 Q2_0 优化的 llama.cpp 工作树。已在对应源码副本实际应用，并核对三个输出文件的 SHA-256 与构建输入一致。基础工作树提交、源文件指纹、逐请求数据和投影重放样本均在 results.json。此次只运行私有实验构建，已核对原服务程序与 HIP 库的 SHA-256。实验使用同一个可执行文件，进程环境中的 `BONSAI_Q2_EIGHT` 和 `BONSAI_Q2_EIGHT_PREP` 同设为 `0` 复现旧八列，同设为 `1` 启用两项优化。原生 MTP7 使用 `--spec-type draft-mtp --spec-draft-n-max 7`。

可在 gfx90a 机器上使用项目对应的 gguf-py 和 ROCm hipcc 重放全部投影。以下命令从本目录运行，`MODEL` 指向原 Q2_0-mtp.gguf，`LLAMA_CPP` 指向该模型兼容的源码树。

```sh
PYTHONPATH="$LLAMA_CPP/gguf-py" python3 make_manifest.py "$MODEL" weights.tsv groups.txt
hipcc -O3 -std=c++17 --offload-arch=gfx90a eight-replay.hip -o eight-replay
./eight-replay weights.tsv groups.txt "$MODEL" 12 0
```
